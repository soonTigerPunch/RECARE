# AI 레시피 추천 — Supabase 구현 설계 보충

기준: 사용자가 첨부한 `2026-11-04-ai-recipe-design.md` v0.2 및
`ee31052`의 Flutter 앱 1.1.1+6.

## 확정 사항과 미확정 사항

- 사용자 요청: 명세에 따른 실제 OpenAI 레시피 추천 구현. 모호한 사항은 질문한다.
- 사용자 선택: Supabase를 새로 구성하여 운영 서버 배포까지 포함한다.
- 개발 환경의 `RECARE_KEY`는 준비 상태이며 값을 출력하거나 앱에 포함하지 않는다.
- 기존 환경 변경을 재적용하거나 클라우드 환경을 게시하지 않는다.
- 확정: 명세 전체 구현 범위와 제안 기본값을 적용한다.
- 확정: OpenAI 잔액 미충전으로 실제/유료 호출은 보류하며 모의 응답으로만 검증한다.
- 운영 배포 전 결정: 프로젝트 계정/리전/요금제, 일일·월간 서비스 예산,
  개인정보 처리 안내, 앱 무결성 검증 및 공개 이용 정책.

## 목적과 범위

남은 재료와 소비기한을 바탕으로 최대 3개의 요리를 제안한다.
수량·재고·저장·취소의 정확성은 모델 판단에 맡기지 않는다.
전체 범위가 확정되면 추천 입력/결과/상세, 최근 5회, 즐겨찾기 100개,
장보기 일괄 추가, 조리 기록의 원자적 저장/취소를 포함한다.
로그인 화면, 동기화, 식단, 이미지 생성, 영양 분석은 포함하지 않는다.

## 접근 방식

기존 프로젝트에는 서버가 없다. 독립 서버와 DB를 별도로 운영하는 방식과
인증·서버 함수·DB를 함께 사용하는 방식을 검토했고, 사용자가 Supabase를 선택했다.
앱 → Supabase 인증/Edge Function → OpenAI Responses API 경로를 사용한다.
OpenAI 키를 Flutter 앱에서 직접 사용하는 방식은 적용하지 않는다.

## 앱 연결

- 기존 홈/목록/설정 하단 메뉴를 유지하고 홈에서 전용 페이지를 연다.
- `RecipeClient` 경계를 두어 HTTP 연결과 화면 테스트를 분리한다.
- 앱에는 Supabase URL과 공개용 publishable key만 설정한다.
- OpenAI 프로젝트 키와 Supabase service-role 키는 서버에만 둔다.
- 인증은 Supabase 익명 인증을 사용하고, 서버에서 토큰 유효성과 세션을 검증한다.
- 추천 버튼에서만 새 작업을 시작한다. 취소 후 늦은 응답은 화면을 이동시키지 않는다.
- 선택 원문 제외 조건은 메모리에만 두고 최근 결과/즐겨찾기에는 저장하지 않는다.
- 소비기한은 기기의 달력 날짜로 재확인한다. 지나거나 재고 0인 항목은 제외한다.
- 현재 `FoodUnit`의 정수 수량을 사용하고, 같은 계열만 변환한다.

## 서버

- Edge Function은 요청을 검증한 뒤 고정된 모델/프롬프트/JSON Schema로 호출한다.
- 입력에는 임시 재료 ID, 이름, 수량/단위, 남은 일수와 필요한 조건만 포함한다.
- `store: false`를 사용하며 구매금액·처리 이력·기기 ID는 모델에 보내지 않는다.
- 결과의 참조 ID, 수량, 단위, 재고 초과, 구매 조건, 명백한 제외 조건을 검사한다.
- 통과한 1~3개를 정렬해 반환하고, 전부 실패했을 때만 시간/예산 내 1회 교정한다.
- 동일 요청 ID는 동일 세션의 동일 작업으로 취급한다. DB 원자적 예약으로
  중복 모델 실행, 일일 한도 경쟁, 서버 전체 예산 초과를 방지한다.
- 요청 ID의 유효기간은 서버가 검증한다. 오래된 ID로 새 모델 작업을 시작하지 않는다.
- 네트워크 결과가 불명확한 요청을 자동으로 다시 생성하지 않는다.
- 작업 저장소는 클라이언트 직접 접근을 막고, 결과는 암호화하여 최대 24시간 보관한다.
- 일반 로그에는 원문 입력/출력·인증 헤더·키를 기록하지 않는다.
- 예산과 공개 이용 정책이 미확정이면 실제 운영용 추천 엔드포인트를 개방하지 않는다.

## 로컬 저장

- SQLite v4로 올려 v1/v2/v3의 기존 재고/기록/장보기/확인 이력을 보존한다.
- 최근 추천, 독립 즐겨찾기 본문, 설정, 조리 작업/기록 연결,
  장보기 일괄 작업 ID를 추가한다. 원문 제외 조건은 영속화하지 않는다.
- 조리 작업 ID를 저장 전 영속화한다. 같은 ID의 재시도는 중복 차감하지 않는다.
- 최신 재고/수량/소비기한을 트랜잭션에서 재검증하고 모든 먹음 기록을 함께 저장한다.
- 실행 취소는 관련 기록 전체가 각각 최신이고 복원 가능할 때만 함께 적용한다.
- 기존 `processFood()` 금액 배분 규칙과 voided 기록 보존 정책을 재사용한다.
- 장보기 중복 기준은 기존 이름/단위 계열/정수 수량 규칙을 유지한다.

## 검증과 배포 경계

기존 정적 검사와 Flutter 테스트 122개는 변경 전 통과했다.
새 검증은 마이그레이션, 강제 DB 실패 롤백, 재시도/재시작 중복 방지,
즐겨찾기 오프라인 유지, 잘못된 AI 응답 차단, 서버 한도 경쟁,
취소 후 늦은 응답, 작은 화면/큰 글씨를 포함한다.
유료 API 검증은 사용자 비용 상한이 확정된 후 수행한다.
서버 배포는 사용자 소유 프로젝트와 필요한 보안 설정을 준비한 뒤 별도 확인한다.
실기기 동작과 공개 운영 정책이 검증되기 전 공개 운영 완료로 표시하지 않는다.
