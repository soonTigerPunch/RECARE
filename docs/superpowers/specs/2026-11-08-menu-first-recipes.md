# 메뉴 선택 후 상세 레시피 생성

사용자 승인: 메뉴명 3~5개 → 하나 선택 → 상세 생성. 테스트 누적 한도 $1. 기존 README 미커밋 변경은 보존한다.

메뉴 화면은 이름만 표시한다. 같은 요리의 이름만 바꾼 후보는 제거한다. 조건이 부족하면 가능한 개수만 반환하며 억지로 메뉴를 채우지 않는다. 추가 구매·기본 양념·제외 조건은 두 단계 모두 적용한다. 메뉴 단계는 조리법을 생성하지 않는다.

API: 기존 POST 요청에 `stage: "menus"` 또는 `stage: "detail"` 추가. 필드 미지정은 기존 버전 유지. 두 단계는 각기 UUID 작업을 발급하고 같은 예약/암호화/재조회/한도 방어를 적용한다. 메뉴 응답은 `{status,message,menus:[{id:"m0",title:"두부구이"}],generated_at}`. detail 요청에는 `parent_request_id` 및 `menu_id`를 포함한다. 서버는 같은 세션의 완료된 메뉴 작업을 복호화하여 메뉴의 존재와 원래 입력 해시(요청 ID 제외)를 확인한 뒤 고정된 선택 제목으로 상세를 생성한다. 클라이언트 임의 제목은 받지 않는다. 상세는 기존 recipes 형식이며 정확히 선택 메뉴 하나만 허용한다. 부모 메뉴는 동일 세션,24시간 이내여야 한다.

각 단계의 재시도는 같은 작업 ID를 조회하고 새 생성하지 않는다. 상세 캐시는 메뉴별 child ID로 재사용한다. 입력 재검증은 새 상세 요청 직전에 실시하고 선택 재고가 바뀌거나 기한이 지난 경우 조건 화면으로 안내한다. 이미 생성된 상세의 재열람에는 재고 변경으로 새 호출을 강제하지 않는다.

누적 테스트 총$1 중 기존 프로그램 예산은 $0.90까지로 올려 이전 프로그램의 모든 사용액을 보존하고, 이전 별도 호출 등 여유 $0.10을 남긴다. 두 단계는 각각 하루5회 작업 한도에 포함한다(완성 추천세트는 최대2건+메뉴1건). 화면/운영문서에 이 정책을 안내한다. 공개 모드와 허용목록 보호는 유지한다.

검증 기록: 실제 Flutter client 메뉴3개(두부조림·양파달걀볶음·두부전)→두부조림 상세→재조회→권한 회수 차단 성공. 모델2회, 총입력1071/출력464토큰, 가격 기준$0.001172. 서버43/Flutter187 테스트와 정적 분석 통과. 실제 Android 설치·화면 검증은 별도 남음.
