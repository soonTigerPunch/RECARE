## 1. 목적과 의사결정 상태

사용자가 냉장고의 남은 식재료로 만들 요리를 찾고, 소비기한이 임박한 재료를 실제로 사용하도록 돕는다. 추천 이후 실제 사용량 확인을 거쳐 기존 먹음 기록과 연결한다. AI는 레시피를 제안하고, 수량 검증과 재고 변경은 앱 코드가 담당한다.

사용자 요구는 AI 레시피 추천 기능 기획이며 LLM을 사용할 경우 OpenAI 제품을 사용한다. 2026-11-04 추가 요청으로 추천 레시피 즐겨찾기를 첫 버전 범위에 포함한다. 홈 진입·로그인 없는 이용·전체 화면 중심 흐름은 지금까지 설명한 권장안이다. 사용자가 세부 설계를 모두 승인한 것으로 간주하지 않는다. 이 문서의 기본값, 한도, 저장 정책은 작성자의 제안이다.

현재 앱은 Flutter와 기기 내 SQLite를 사용하며 서버·사용자 계정이 없다. 하단 메뉴는 홈/목록/설정이고, 장보기는 상단 버튼으로 접근한다. 식재료는 이름, 단위, 남은 수량, 소비기한을 가진다. 기존 DB는 버전 3이다.

## 2. 접근 방식과 첫 버전 범위

### 배치 대안

| 방식 | 장점 | 제약 | 제안 |
| --- | --- | --- | --- |
| 홈 카드에서 전용 화면 진입 | 소비기한 확인과 요리 추천을 연결하고 기존 메뉴 유지 | 반복 이용자는 홈을 거침 | 첫 버전 권장 |
| 독립 레시피 탭 추가 | 추천·저장·식단 기능 확장에 유리 | 현재 기능 규모에 비해 메뉴가 늘어남 | 반복 사용 확인 후 검토 |
| 팝업 안에서 전체 기능 제공 | 짧은 진입 | 재료 선택·긴 조리 순서를 읽기 어려움 | 짧은 안내·확인에만 사용 |

### 추천 생성 대안

첫 버전은 OpenAI의 텍스트 생성과 구조화 출력을 사용한다. 레시피 DB 검색과 AI 설명을 결합하는 방식은 검증된 원본과 이용 권한 확보가 필요하므로 후속 대안으로 남긴다. 첫 버전에는 검색 출처가 있는 레시피로 표시하지 않는다.

포함: 재료 선택, 조건 설정, 최대 3개 추천, 상세 조리법, 부족 재료의 장보기 추가, 조리 후 일괄 먹음 기록, 최근 추천·즐겨찾기 기기 내 저장, 오류·오프라인 처리.

후속 범위: 로그인·동기화, 주간 식단, 채팅형 조리 상담, 사진 분석, 음식 사진 생성, 정밀 영양·칼로리, 의료·치료 목적 식단, 유료 구독, 검증된 외부 레시피 검색.

## 3. 대표 사용 시나리오

사용자가 홈에서 오늘까지인 두부 300g과 1일 남은 애호박 200g을 확인한다. 추천 카드에서 재료 선택 화면으로 들어간다. 두부·애호박을 선택하고 달걀을 추가한 뒤, 1인분·20분 이내·추가 구매 없음으로 추천받는다. 최초에는 전송 정보 안내를 확인한다. 추천 중 두부 애호박 달걀볶음을 열어 조리한다. 사용량 확인 화면에서 실제 두부 사용량을 150g에서 100g으로 수정하고 저장한다. 앱은 여러 재료의 먹음 기록을 하나의 작업으로 저장하고 남은 재고를 갱신한다.

## 4. 화면 구성과 전환

주 흐름: 홈 → 재료·조건 선택 → 추천 결과 → 레시피 상세 → 사용량 확인 → 완료 후 상세 복귀.

홈에는 기존 하단 메뉴를 유지한다. 추천 흐름의 전용 페이지에는 상단 뒤로가기와 화면별 행동 버튼을 사용한다. 추천 입력·상세 페이지에는 하단 메뉴를 표시하지 않는다. 뒤로가기는 입력과 결과를 보존한다. 진행 중 작업을 버리고 홈으로 나갈 때만 필요한 확인을 제공한다.

### H01 홈 진입

- 기존 폐기금액·임박재료 영역과 식재료 등록 기능을 유지한다.
- '먼저 확인할 재료' 제목 근처에 '요리 찾기' 버튼을 두어 재료 목록이 길어도 접근할 수 있게 한다. 임박 목록 아래에는 요약 추천 카드를 둔다. 한 화면에 진입점이 중복되어 복잡해지면 제목 버튼만 유지하도록 디자인 검토한다.
- 임박 재료가 있으면 '두부·애호박으로 요리 찾아보기', 없으면 '냉장고 재료로 오늘의 요리 찾기'를 표시한다.
- 재고가 없으면 '식재료를 등록하면 요리를 추천해드려요'와 등록 버튼을 표시한다.
- '최근 추천'과 '즐겨찾기'는 카드의 보조 링크로 제공하고, 결과가 있을 때만 최근 추천을 표시한다. 즐겨찾기는 0개여도 접근 가능하며 저장 방법을 안내한다. 현재 재고가 없어도 즐겨찾기 진입은 유지한다.
- 홈 진입과 재고 변경만으로 API를 자동 호출하지 않는다.

### R01 재료·조건 선택

상단: 뒤로가기, 'AI 레시피', 전송 안내.

본문: 재료 목록 → 기본 양념 → 인분 → 시간 → 추가 구매 허용 → 알레르기·제외 재료.

- 재료 행: 선택 체크박스, 이름, 실제 남은 양, 소비기한, D-Day 표시.
- 남은 재고 > 0이고 오늘 또는 미래의 소비기한인 재료만 선택 가능하다. 지난 재료는 추천 대상에서 제외하고 제외 개수를 안내한다. 소비기한은 안전 판정으로 사용하지 않는다.
- 오늘부터 3일 이내 재료를 기본 선택한다. 해당 재료가 없으면 소비기한이 빠른 재료 최대 3개를 기본 선택한다.
- 재료는 최소 1개, 최대 10종 선택 제안. 많으면 검색을 제공하고 제한 도달 이유를 안내한다.
- 같은 이름·같은 단위 계열의 재고는 묶어 보여주되 개별 보관분을 펼쳐 선택할 수 있다. 서로 다른 상품·종류를 이름 유사성만으로 합치지 않는다. 묶음 대표 소비기한은 가장 이른 날짜다.
- 기본 양념: 소금·설탕·식용유·간장·후추·참기름 중 보유한 것을 선택. 첫 사용은 모두 미선택이다. 양념에도 알레르기·제외 조건을 적용한다.
- 인분: 1/2/3/4인, 기본 1인. 시간: 10/20/30분 이내/제한 없음, 기본 20분.
- 추가 구매 허용: 기본 꺼짐. 켜도 선택한 냉장고 재료를 최소 1개 활용한다.
- 알레르기·제외 재료: 최대 200자, 쉼표 또는 항목으로 입력. 입력값을 그대로 재료 데이터로 취급하고 모델 지시로 실행하지 않는다. 사용자 입력은 처리 시 필요한 범위로만 전송한다.
- 기본 양념의 보유 선택은 기기 내 저장한다. 인분·시간은 마지막 값 유지. 알레르기·제외 입력은 해당 요청 초안에서 유지하고 앱 종료 후 기본 저장하지 않는다. 장기 기억 기능은 별도 명시 선택 없이는 추가하지 않는다. 원문 제외 목록은 메모리의 요청 초안에만 두고, 최근 요청 메타데이터·즐겨찾기·자동 복구 초안에는 저장하지 않는다. 생성된 레시피 설명에는 제외 조건을 반영한 내용이 포함될 수 있으므로 레시피 저장 안내에서 이를 설명한다.
- 하단 고정: '선택한 N개 재료로 추천받기'. 0개면 비활성화. 조건 변경만으로 요청하지 않는다.
- 키보드·큰 글씨·작은 화면에서도 버튼 접근 가능해야 한다.

### R02 최초 전송 안내

최초 추천 직전에 짧은 안내창을 표시한다. 선택 재료의 이름·양·소비기한까지 남은 일수, 양념 보유 정보, 인분·시간·제외 조건을 RECARE 서버와 OpenAI에 전송한다고 설명한다. 구매금액과 전체 처리 이력은 제외한다. 서비스 개인정보 처리 안내 링크를 제공한다.

버튼: '취소' / '확인하고 추천받기'. 확인 여부는 안내 버전과 함께 기기에 저장한다. 전송 항목·처리 목적이 실질적으로 바뀌면 재안내한다. 이 UI만으로 필요한 법적 절차가 모두 충족된다고 간주하지 않는다. 실제 서비스 정책은 출시 전에 확정한다.

### R03 추천 진행

'선택한 재료로 요리를 찾고 있어요'와 진행 표시. 동일 요청 중 버튼 중복 입력을 막는다. 취소하면 입력 화면으로 돌아가며 늦게 도착한 응답이 화면을 다시 열지 않게 한다. 취소 전에 이미 시작된 OpenAI 요청의 비용은 발생할 수 있다.

서버 전체 처리 제한은 초기 30초 제안, 앱 대기 제한은 35초 제안이다. 실제 모델 측정 후 조정한다. 입력 조건은 실패·취소 후 보존한다.

### R04 추천 결과

- 상단: 선택한 재료·인분·시간 요약, 조건 수정.
- 카드 최대 3개: 요리명, 예상 시간, 인분, 사용할 재료와 양, 임박 재료 활용 이유, 부족 재료 개수, 상세 버튼.
- 각 카드 우측 상단에 별 토글을 둔다. 비선택 별은 '즐겨찾기 추가', 선택 별은 '즐겨찾기 해제'다. 별 버튼은 상세 진입과 별도 터치 영역으로 제공하고 스크린리더에 요리명과 현재 선택 상태를 전달한다.
- 조건을 만족하는 요리가 1~2개뿐이면 그대로 표시하고 부족 이유를 설명한다. 3개를 맞추기 위해 조건을 임의로 완화하지 않는다.
- 결과 순서는 임박 재료 활용 → 추가 구매 종류 수가 적음 → 예상 시간이 짧음 순으로 서버에서 정렬한다. 각각의 요리는 독립적인 대안이며 세 요리를 모두 조리할 재고가 있다고 의미하지 않는다.
- '추가 구매 없음'은 입력된 재료·보유 양념을 기준으로 산정한다. 미확인 양념을 자동 보유로 간주하지 않는다.
- 조건 수정은 기존 선택값으로 돌아간다. 수정 후 명시적으로 추천 요청해야 새 호출한다.
- 기존 결과를 다시 열 때의 재고 변화는 '추천 당시 재고 기준'으로 표시한다. 조리 전 최신 재고 확인을 제공하고, 부족해진 경우 재추천 또는 사용량 조정을 안내한다.

### R05 레시피 상세

- 상단: 제목, 예상 시간, 인분, 'AI가 제안한 레시피', 즐겨찾기 별 버튼. 추천 카드와 같은 즐겨찾기 상태를 공유한다.
- 추천 이유, 필요한 재료·수량/현재 보유량, 사용 보관분을 표시한다.
- 추가 구매 항목과 기본 양념을 분리 표시한다. 장보기 추가 전 구매 수량을 확인한다.
- 조리 순서는 번호를 붙여 표시한다. 알레르기 및 재료 상태 확인 안내를 제공하되 이를 안전 보증으로 표현하지 않는다.
- 하단 고정: '만들었어요 · 사용량 확인'. 조회·저장만으로 재고를 변경하지 않는다.
- 상세 열기와 저장에는 OpenAI 호출이 없다. 인분 변경은 상세에서 단순 곱셈하지 않고 조건 수정 후 재추천하도록 한다.

### R06 사용량 확인

- 레시피의 재고 연결 재료를 표시하고 제안 사용량을 채운다. 실제 사용량을 수정하거나 0으로 제외할 수 있다.
- 최신 보관분별 재고·사용량·저장 후 남는 양을 보여준다. 기본 배분은 소비기한이 빠른 선택 보관분부터 사용한다. 이름은 같아도 다른 재고를 사용자 모르게 대체하지 않는다.
- 기존 단위 체계를 유지한다. g↔kg, ml↔L만 동일 계열에서 정확히 변환하고 무게↔부피↔개수 간 임의 환산은 금지한다. 개수의 부분 사용은 기존 앱 규칙과 같이 허용한다. 부동소수점 계산으로 내부 수량을 저장하지 않는다.
- 추천 이후 실제 사용한 등록 재료가 달라졌다면 '재료 바꾸기/추가'로 현재 재고에서 다시 선택할 수 있다. 같은 재고를 중복 선택할 수 없다. 추가 구매 재료가 등록되지 않았으면 재고를 새로 만들지 않는다. '재고에서 확인되지 않은 재료는 이번 기록에 반영되지 않아요'를 표시한다.
- 재고 이하의 유효 수량이고 양수 항목이 1개 이상일 때만 저장 가능하다. 저장을 누르면 해당 보관분의 상태를 다시 검증한다. 삭제, 수량 변경, 소비기한 변경 또는 날짜가 바뀌어 기한이 지난 경우 부분 저장 없이 재확인을 요구한다.
- 조리에 투입한 양을 기존 '먹음' 기록으로 관리한다는 현재 앱 기준을 따른다. 조리 후 남긴 완성 음식의 재고나 실제 섭취량을 별도로 추적하지 않는다.
- 여러 먹음 기록과 조리 작업 상태를 하나의 DB 트랜잭션으로 저장한다. 한 항목 실패 시 전체 취소한다.
- 같은 저장 요청의 중복 탭·재시도·앱 재시작으로 차감이 반복되지 않도록 작업 ID를 영속화한다. 재시도는 같은 ID를 쓰고, 새로 요리한 경우 별도의 확인으로 새 작업 ID를 만든다.
- 완료 후 상세로 돌아가 '먹음 기록 N건을 저장했어요'와 기존 기준의 8초 실행 취소 제공. 같은 조리 회차의 기록 전체를 한 번에 되돌린다.
- 실행 취소는 각 관련 재료에서 해당 기록이 최신 유효 기록이고 재고 복원이 가능할 때만 허용한다. 하나라도 불가능하면 전체 복원을 하지 않고 안내한다. 취소 이력은 보존한다.
- 이미 기록한 조리 회차에는 '기록 완료' 표시. '다시 만들었어요'로 명시적으로 새 회차를 시작할 수 있다. 늦게 완료된 저장이 이전 화면의 버튼 상태를 되돌리지 않게 한다.

### R07 최근 추천

홈의 '최근 추천'에서 전체 화면 목록으로 연다. 마지막 5회 요청 결과를 유지한다. 각 결과의 별 버튼으로 즐겨찾기를 추가·해제할 수 있다. 최근 결과에서 빠지거나 전체 추천 이력을 삭제해도 즐겨찾기는 남는다. 최근 추천이 없으면 추천 시작 화면으로 안내한다.

### R08 즐겨찾기

**진입과 목록**

- 홈 추천 카드의 '즐겨찾기' → 전체 화면 목록 → 레시피 상세로 이동한다. 별도 하단 메뉴는 추가하지 않는다.
- 상단에 뒤로가기, '즐겨찾기', 저장 개수를 표시한다. 요리명과 주요 재료로 기기 내 검색한다.
- 목록 카드는 요리명, 예상 시간, 원래 인분, 주요 재료, 선택된 별을 표시한다. 기본 정렬은 최근 즐겨찾기한 순서이며 열람만으로 순서를 바꾸지 않는다.
- 0개면 '다시 만들고 싶은 요리를 별표로 저장해보세요'와 '레시피 추천받기'를 표시한다. 재고가 없으면 등록 안내로 연결한다. 검색 결과가 없으면 저장 목록을 지우지 않고 검색어 수정·초기화를 제공한다.

**저장과 해제**

- 추천 카드·최근 추천·상세·즐겨찾기 목록의 별 상태는 즉시 일치해야 한다. DB 저장 성공 시 '즐겨찾기에 추가했어요'를 알린다. 실패하면 원래 상태를 유지/복원하고 다시 시도할 수 있게 한다.
- 저장 항목은 요리명, 인분, 예상 시간, 정확한 재료·수량·단위, 추가 재료·양념, 조리 순서, 생성 및 저장 시각, 레시피 형식 버전이다. 목록에서 사라져도 상세를 열 수 있도록 전체 레시피를 독립적으로 보관한다.
- 원문 알레르기·제외 목록과 추천 요청 전체를 즐겨찾기에 복사하지 않는다. 생성 본문은 해당 조건을 반영한 내용을 포함할 수 있음을 저장 안내에서 설명한다.
- 앱이 부여한 레시피 ID로 중복 저장을 막는다. 같은 레시피의 여러 화면에서 별을 눌러도 항목이 늘지 않는다. 재생성으로 얻은 다른 ID는 이름이 같아도 다른 레시피로 취급한다.
- 다시 별을 누르면 해제하고 '즐겨찾기에서 해제했어요 · 실행 취소'를 8초 제공한다. 해제는 먹음 기록·조리 이력·최근 추천을 삭제하지 않는다. 원래 추천 이력이 없어도 과거 조리 기록을 보존한다.
- 최대 100개는 초기 제안으로 유지한다. 한도 도달 시 기존 항목을 해제하도록 안내하며 임의로 가장 오래된 항목을 삭제하지 않는다.

**다시 요리하기와 오프라인**

- 저장·해제·검색·재열람에는 OpenAI 호출과 추천 횟수 차감이 없다. 인터넷이 없어도 동작한다.
- 상세에 '저장 당시 레시피예요. 현재 재고와 알레르기 조건을 확인해주세요'를 표시한다. 과거 '오늘까지'·'추가 구매 없음' 표시를 현재 상황에 그대로 재사용하지 않는다.
- 재료 이름·종류·단위 계열을 참고해 현재 재고 연결 후보를 제시하되 사용자가 확인한다. 기존 보관분이 삭제됐다고 비슷한 상품으로 자동 대체하지 않는다. 단위 환산이 불가능하면 수량 확인을 요구한다.
- '만들었어요 · 사용량 확인'으로 현재 사용 재고를 선택하고 R06의 일괄 저장 규칙을 적용한다. 즐겨찾기의 원본 수량·조리법은 수정하지 않는다. 등록되지 않은 재료는 해당 사실을 안내하고 재고에서 차감하지 않는다.
- 현재 조건으로 다른 요리가 필요하면 '이 재료로 다시 추천'으로 R01에 이동한다. 선택값을 검토한 뒤 추천 버튼을 누를 때만 새 호출하며, 원래 즐겨찾기를 덮어쓰지 않는다.
- 이전 제외 목록은 복원하지 않으며 오프라인 열람으로 새로운 제외 조건에 대한 AI 재검증이 이루어진 것으로 표시하지 않는다.
- 앱 삭제 시 함께 삭제되며 기기 간 동기화는 제공하지 않는다. 즐겨찾기에는 기기 저장임을 안내한다.

## 5. 장보기 연결

미보유 재료와 양념은 '장보기 항목 확인' 화면에서 사용자가 선택한다. 레시피 필요량을 참고 정보로 표시하고 구매 단위·수량을 확인받는다. '약간', '1큰술'을 기존 g/ml/개로 임의 변환하지 않는다. 정확한 기존 단위의 구매량 입력이 있어야 추가한다.

이름·단위 계열·수량의 기존 중복 기준을 사용하고 같은 이름이라도 수량이 다르면 조용히 합산하지 않는다. 일괄 추가는 하나의 트랜잭션과 재요청 ID로 처리한다. 결과에 새로 추가한 개수와 기존 동일 항목 개수를 구분한다. 자동 구매·자동 재고 등록은 하지 않는다.

## 6. 추천 규칙과 한계

1. 선택 재료 전체를 반드시 쓰도록 강제하지 않고 최소 1개를 활용한다. 임박 재료 활용을 우선한다.
2. 요리 하나에 필요한 양은 선택한 사용 가능 재고량 이내여야 한다. 0·음수·비정상 단위는 거절한다.
3. 소비기한이 지난 재료와 0 재고를 입력 대상에서 제외한다. 날짜는 요청 시 사용자 기기의 달력 날짜를 기준으로 하며 대기·재진입 후 다시 확인한다.
4. 추가 구매 허용이 꺼져 있으면 선택 재료와 사용자가 확인한 기본 양념만 사용한다. 허용 시에도 새 필수 식재료는 최대 3종을 제안 기본값으로 한다. 실제 필요한 추가 재료는 양념을 포함해 모두 표시한다.
5. 입력된 알레르기·제외 재료와 알려진 포함 성분을 프롬프트와 서버 검사에 반영한다. 동의어·복합 양념 검사는 제한적이며 완전한 알레르기 안전 판정을 제공하지 않는다. 사용자는 제품 표시를 확인해야 한다.
6. 요리 이름만 바꾼 중복 제안을 줄인다. 불확실한 조리 시간은 예상값으로 표시하고 실제 안전 온도·익힘 상태를 확인하는 안내를 넣는다.
7. 사진·영상·웹 검색·외부 원문 인용을 요청하지 않는다. 정확한 출처와 검증된 영양 정보를 가진 레시피로 표시하지 않는다.

## 7. OpenAI 연동 및 서버 동작

앱 → HTTPS 추천 서버 → OpenAI Responses API → 서버 검증 → 앱의 카드·상세 화면 순서다. 키는 서버의 비밀값으로 관리한다. 앱에는 서버 주소와 앱 전용 익명 인증 정보만 사용한다. OpenAI 프로젝트 키는 앱에 배포하지 않는다.

API 초안: `POST /v1/recipe-recommendations`. 앱 전용 요청 ID와 익명 세션으로 중복 요청을 구분한다. 서버는 입력 크기·타입·재료 수·수량·시간·인분·한도를 검증한다. 모델과 출력 제한, 프롬프트는 서버가 선택하며 클라이언트가 변경할 수 없다.

OpenAI로 전송: 요청 안에서만 사용하는 재료 ID, 이름, 정규화한 남은 양·단위, 남은 일수, 기본 양념, 인분, 시간, 추가 구매 허용, 제외 조건. 기기 식별자·세션 토큰·구매금액·전체 처리 이력·직접 식별정보는 모델 입력에서 제외한다. 로컬 재고 ID와 모델용 임시 ID의 대응은 앱 요청 문맥에서 관리한다.

응답: 상태(ok/no_match), 추천 요리 목록, 요리별 제목·인분·예상 시간·사용 재료 ID/양/단위·추가 재료/양념·추천 이유·단계·확인 안내. 필요한 수량은 정확히 해석 가능한 형식으로 전달하고 추가 재료의 '적당량' 같은 텍스트와 구분한다. 서버의 JSON Schema로 응답 구조를 지정한다.

서버 검증은 입력 ID 참조, 수량/단위 호환성, 재고 초과, 구매 조건, 명백한 제외 재료, 중복 요리, 출력 크기를 포함한다. 거절·불완전 응답은 정상 결과로 처리하지 않는다. 앱도 로컬 입력 문맥과 결과를 재검증한다. 모델이 반환한 '추가 구매 없음'이나 임박도 표시는 그대로 신뢰하지 않고 입력과 결과로 계산한다.

최대 3개 요리의 상세까지 정상 호출 1회로 생성한다. 일부만 통과하면 그 결과를 제공한다. 전부 검증 실패인 경우에만 남은 서버 제한 시간·비용 한도 안에서 교정 호출을 최대 1회 허용한다. 전송이 시작된 뒤 결과를 알 수 없는 타임아웃에는 무조건 새 요청하지 않는다. 한 사용자 요청에 대한 OpenAI 호출은 최대 2회다.

키/모델 접근 오류·과금 한도 오류는 운영 오류로 분류하고 사용자에게 반복 재시도를 유도하지 않는다. 429/일시 장애는 재시도 가능한 상태로 표시한다. 클라이언트 재시도는 동일 요청 ID로 작업 상태를 조회/재수신하고, 서버의 잠금으로 진행 중 작업을 중복 시작하지 않는다. 재료별 레시피 본문을 재사용하는 공용 캐시는 첫 버전에 도입하지 않는다. 서버가 검증 가능한 작업 ID의 유효기간은 24시간으로 정하고, 결과 보관기간이 지난 ID에는 만료 응답을 반환하며 같은 ID로 새 모델 작업을 시작하지 않는다. 새 추천은 사용자 행동으로 새 작업을 시작해야 한다. 작업 ID 발급·서명 방식은 구현자가 정한다.

응답 저장 옵션은 `store: false` 방향으로 설정한다. 이것만으로 OpenAI의 모든 로그 보관이 없어지는 것으로 설명하지 않는다. 정확한 데이터 처리·보관은 선택 모델·계정 정책과 공식 문서를 출시 시점에 다시 확인한다. 상시 대화 세션·모델 학습·파일 업로드는 첫 버전에 필요하지 않다.

## 8. 로그인 없는 운영과 비용 통제

프로토타입은 테스트용 익명 세션과 서버 전체 호출 상한으로 검증한다. 공개 배포에서는 서버가 발급한 만료·갱신 가능한 익명 세션, 세션별 요청 제한, 짧은 시간의 IP별 제한, 앱 무결성 검증을 조합한다. IP만으로 일일 사용자 한도를 정의하지 않는다. 앱 공통 비밀문자열만으로 앱의 진위를 판단하지 않는다. 재설치로 제한을 우회할 수 있는 한계와 대응 비용은 운영 정책에 포함한다.

초기 제안: 익명 세션당 한국 시간 하루 5회 신규 추천, 동시 진행 1건. 최근 결과 열람과 같은 요청 ID의 재수신은 새 추천으로 세지 않는다. 처리 시작 시 한도를 예약하고 정상 결과 또는 정상 no_match는 차감, 서비스 오류는 해제한다. 모델 토큰 비용은 실패 시에도 발생할 수 있으므로 서버 전체 비용 상한에는 포함한다. 거절된 악성 요청 반복은 별도 속도 제한한다.

전체 서비스의 일일·월간 예산 숫자는 미정이며 공개 배포 전 필수다. 요청별 최대 비용과 최대 동시 작업을 기준으로 예산을 선점하고 사용량 정산으로 초과 발행을 막는다. 운영자가 추천 기능을 즉시 중지할 수 있도록 서버 플래그를 둔다. 기존 재고·장보기 기능은 계속 동작한다.

서버에는 요청 ID, 익명 세션의 가명 식별자, 모델/프롬프트 버전, 토큰 사용량, 지연시간, 오류 코드만 기본 기록한다. 원문 재료·알레르기 입력·API 키는 일반 로그에서 제외한다. 중복 요청 처리용 결과는 접근을 해당 세션으로 제한해 암호화된 작업 저장소에 최대 24시간 보관하는 안을 제안한다. 익명 세션은 30일 만료·갱신, 사용량·오류 로그는 30일 후 삭제를 제안한다. 실제 저장소와 보관정책은 배포 서비스 선택에 맞춰 확정한다.

## 9. 로컬 데이터와 기존 기능 영향

레시피 요청 결과, 최근 요청 목록, 즐겨찾기, 조리 작업, 조리 작업-먹음 기록 연결, 전송 안내 버전을 저장할 구조를 추가한다. 최근 결과·즐겨찾기의 저장 필드에서 원문 알레르기·제외 목록을 제외한다. 레시피 본문이 조건을 간접적으로 반영할 수 있다는 사실은 별개로 안내한다. 재고 기록 테이블의 기존 금액 배분·취소 이력을 유지한다. 새 DB 버전으로 올리고 v1/v2/v3에서 데이터 손실 없이 이전하는 검증이 필요하다. 테이블 상세 이름과 인덱스는 구현자에게 맡기되 원자적 저장·중복 방지·조리 회차별 취소를 충족해야 한다.

현재 `process()`와 `undoProcess()`는 재료 1건 단위다. 단순히 여러 번 호출해서 일괄 성공으로 취급하면 부분 저장/부분 취소가 생긴다. 여러 재료에 대한 저장 및 취소의 별도 트랜잭션 처리가 필요하다. 장보기 일괄 추가도 같은 원칙을 적용한다.

기존 소비기한 확인 팝업은 추천 입력·상세·기록 화면 위에 끼어들지 않는다. 홈으로 돌아왔을 때 기존 확인 정책에 따라 표시한다. AI 추천만으로 기존 오늘 확인 여부를 갱신하지 않는다. 조리로 재고가 0이 되면 기존 재고·알림 대상 계산을 다시 실행한다. iOS 알림 지원 여부는 이 기능과 별개로 유지한다.

## 10. 예외 상태와 사용자 안내

| 상황 | 동작·문구 |

| 기본 양념 없음·재료 부족 | 가능한 결과만 제시하거나 조건 수정 안내; 자동 구매 허용 금지 |
| 인터넷 없음 | '추천에는 인터넷 연결이 필요해요'; 최근·저장 레시피 열람 가능 |
| 시간 초과 | 선택값 유지, 같은 요청 상태 확인 후 안전한 재시도 제공 |
| 사용자 취소 | 입력으로 복귀, 늦은 응답으로 이동하지 않음; 작업 비용이 발생할 수 있음 |
| 일부 추천만 유효 | 통과한 결과만 표시; 추가 요청을 강제로 하지 않음 |
| 모델 거절·구조 오류 | 오류 상태로 표시하고 제한된 교정 정책 적용; 원문 오류 노출 금지 |
| 일일 한도 도달 | 재이용 가능 시각과 최근 결과 링크; 로그인 강요 없음 |
| 서버 전체 예산 도달 | 새 추천 일시 중지, 기존 재고 기능·저장 레시피 유지 |
| 조리 중 재고 변경 | 최신 값과 변경 항목 표시, 입력 보존, 전체 저장 전 재확인 |
| 저장 실패·앱 종료 | 영속 작업 ID로 실제 저장 결과 확인 후 재시도, 중복 차감 없음 |
| 일괄 실행 취소 불가 | 부분 복원 없이 원인 안내, 원래 기록은 유지 |

## 11. 검증과 출시 판단

출시 전 필수 기능 검증:

- 기한 지난/0 재고가 추천 입력에 들어가지 않는다. 자정 이후·앱 재개 때도 동일하다.
- 기본 양념을 보유로 확인하지 않았을 때 몰래 사용하지 않는다. 제외 조건에 걸리는 양념을 허용하지 않는다.
- 3개의 대안 각각에 대해 재고량·단위·구매 조건을 검사한다. 무게와 개수 환산을 생성하지 않는다.
- 정상 흐름에서 추천 요청 1회 외에 카드 열기·상세·즐겨찾기·재고 저장에 OpenAI 추가 호출이 없다.
- 입력 재료명에 지시문이 들어가도 서버 지시나 모델/도구 설정을 바꾸지 않는다.
- 저장 연속 탭, 네트워크 재시도, 저장 직후 앱 종료에서 중복 차감이 없다.
- 일괄 기록 중간 실패와 일괄 취소 중간 실패가 전체 롤백된다.
- 기존 금액 배분, 폐기금액 통계, 부분 수량, 최신 기록 취소 제한을 보존한다.
- v1/v2/v3 DB를 새 스키마로 이전해 기존 재고·기록·장보기·확인 이력이 보존된다.
- 즐겨찾기 중복 탭·재시작 후에도 하나의 레시피는 하나의 항목으로 남고, 카드와 상세의 별 상태가 일치한다.
- 최근 추천 정리·이력 삭제 후에도 즐겨찾기 상세가 유지되고, 즐겨찾기 해제로 과거 먹음 기록이 삭제되지 않는다.
- 오프라인 즐겨찾기 검색·상세·해제·해제 실행 취소에 OpenAI 호출이 없다. 재고 삭제·변경 후 다시 조리할 때 현재 재고를 확인한다.
- 즐겨찾기 저장 실패·100개 한도·빈 목록·검색 결과 없음 상태에서 데이터 손실 없이 안내한다.
- 작은 화면, 큰 글씨, 다크 모드, 스크린리더에서 선택·단위·오류·고정 버튼을 사용할 수 있다.
- 앱 패키지·Git·오류 응답·일반 로그에 OpenAI API 키가 포함되지 않는다.
- 익명 세션 위조/만료, 한도 경쟁, 중복 요청 ID, 전체 예산 차단을 서버 테스트로 검증한다.

대표 품질 평가에는 임박 재료 1개/여러 개, 양념 없음, 소량 재고, 4인분 부족, 복수 보관분, 부분 개수, 제외 재료·복합 양념, 비요리 재료명, 조건 만족 불가 사례를 포함한다. 명시 조건 위반과 재고 오류가 발생한 사례는 수정·재평가한다. 요리의 타당성과 한국어 안내는 사람이 검토한다. 실제 생성 품질·지연시간·비용은 아직 측정하지 않았다.

이용 흐름 확인을 위해 기기 내 집계 또는 별도 동의를 받은 최소 분석으로 추천 진입, 요청 완료, 상세 열람, 먹음 기록 연결을 살펴본다. 원문 재료·알레르기 입력을 분석 이벤트에 포함하지 않는다. 여러 레시피 페이지의 독립 목적 방문과 반복 이용을 확인한 뒤 레시피 하단 탭 전환을 검토한다. 단순 클릭 증가를 폐기 감소의 증거로 해석하지 않는다.

## 12. 진행 순서와 남은 결정

진행 순서: 기획·운영 범위 확정 → 가짜 응답으로 Flutter 흐름과 로컬 일괄 기록 구현 → 서버·OpenAI 연결 → 품질/비용 평가 → 실기기 QA → 제한된 테스트 배포. 이 문서는 작업별 구현 계획과 별개다.

구현 시 작성자가 결정해도 되는 항목: Flutter 파일 구성, 서버 내부 모듈, DB 테이블 상세, JSON Schema 세부, 접근성 구현, 같은 계열 단위의 정확한 변환 방식.

실제 API 작업 전에는 별도로 키 재사용/신규 발급 의사를 확인하고 비밀값 저장 위치를 확정한다. 현재 문서 작업에는 키 생성·검사·API 호출이 필요 없다.

사용자·운영자의 결정이 필요한 항목:

1. 즐겨찾기는 사용자 요청으로 첫 버전에 포함한다. 최근 추천·조리 후 일괄 기록까지 같은 출시 범위에 포함할지는 이 문서의 제안이다.
2. 추가 구매 기본 꺼짐, 기본 양념 명시 선택, 최대 10종/인분 1~4 등의 제안값 승인 또는 변경.
3. 로그인 없이 제공할 일일 횟수와 서비스 전체 월간 예산, 서버 운영 주체·배포 계정. 문서의 하루 5회는 제안이며 예산 숫자는 미정이다.
4. OpenAI 전송 항목, 익명 세션·서버 결과·로그 보관 정책. 실제 개인정보 안내와 배포 전 정책 확인 필요.

모델명, 배포 서비스, 앱 무결성 검증 공급자는 미선정이다. 모델은 현재 지원 여부와 실제 품질·비용 평가로 고르고, 배포 서비스는 비밀값 저장·영속 작업 저장소·한도 선점·익명 세션 검증을 지원해야 한다. 서버 전체 예산, 무결성 검증, 개인정보 안내를 확정하지 않은 상태에서는 공개 운영 완료로 간주하지 않는다.
