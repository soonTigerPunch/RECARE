# RE:CARE 실제 AI 레시피 추천 테스트 명세

관련 문서: [기존 기획](2026-11-04-ai-recipe-design.md), [서버 계약](../../AI_RECIPE_CONTRACT.md), [서버 운영](../../AI_RECIPE_SERVER.md)

## 1. 목표와 완료 기준

테스트 사용자가 실제 앱에서 보유 재료를 선택하고 추천을 요청하면, Supabase를 통해 OpenAI가 생성한 유효한 레시피를 앱에서 볼 수 있다. 실패해도 입력과 기존 재고는 보존한다. **추천을 사용할 수 없는 APK는 이 기능의 테스트 완료로 보지 않는다.**

이번 목표는 제한된 테스터용 실제 추천이다. 누구나 이용할 수 있는 공개 서비스는 별도 정책과 운영 예산을 확정한 뒤 진행한다. 재고·장보기·즐겨찾기 등 기존 범위는 유지한다.

## 2. 확인된 현재 상태

- Flutter 입력·결과·최근 추천·즐겨찾기·장보기·조리 기록과 서버 코드가 구현돼 있다.
- 새 Supabase 프로젝트에 DB 마이그레이션, 익명 로그인, Edge Function, 정리 스케줄이 배포돼 있다. DB 예산은 0, 추천 기능은 비활성이다.
- Supabase의 `OPENAI_API_KEY`를 사용하는 별도 임시 함수에서 모델 생성과 결과 검사 1회가 성공했다. **실제 앱→인증→작업 발급→예약→생성→저장→앱 표시 경로는 아직 성공 검증되지 않았다.**
- 기존 세션 일일 제한·예산 선점·암호화 결과 보관 코드가 있다. 공개 정책 승인 플래그, 신뢰할 IP 헤더, 모델 가격 및 DB 예산 없이는 기능이 차단된다.
- 사용자 PC의 원본 서명 인증서와 동일한 키로 테스트 APK를 빌드한 적이 있다. 실제 기기 업데이트와 데이터 유지 여부는 미검증이다. GitHub 테스트 릴리스는 파일 업로드 인증 오류로 미완료다.

## 3. 사용자 경험

1. 홈에서 요리 찾기를 연다. 기한이 지나지 않고 남은 양이 있는 재고를 보여주며, 재료·인분·시간·보유 기본 양념·추가 구매 허용·제외 조건을 확인한다.
2. 최초 요청 전 전송 대상(선택 재료명·양·단위·남은 일수, 선택 조건과 제외 조건), OpenAI 처리, 추천의 한계를 안내하고 확인받는다. 직접 식별정보·구매금액·전체 재고 이력을 보내지 않는다.
3. 사용자가 추천 버튼을 눌렀을 때만 새 작업을 시작한다. 로딩·취소·오류 상태에서 입력을 유지한다. 취소는 이미 시작한 모델 호출 비용을 취소하지 않는다.
4. 서버가 검증한 요리 최대 3개 또는 조건에 맞는 요리가 없다는 결과를 보여준다. 후보가 일부만 유효하면 통과한 것만 표시한다. 상세에는 재료·양·단계·예상 시간과 재료 상태·제품 표시·익힘을 확인하라는 안내를 제공한다. 알레르기 안전이나 정확한 영양·출처를 보장하지 않는다.
5. 최근 결과와 즐겨찾기는 기기에 저장한다. 상세 열람·즐겨찾기·장보기 추가·조리 기록은 새 OpenAI 호출을 하지 않는다. 조리 기록은 사용량을 확인받고 한 트랜잭션에서 처리한다.
6. 허용되지 않은 테스터, 예산 소진, 오프라인, 타임아웃, 서버 오류를 구분해 안내한다. 사용자가 한도 초과나 설정 오류에서 반복 요청하도록 유도하지 않는다.

## 4. 제한 테스트 접근과 운영 경계

권장안은 **서버 측 테스터 허용 목록**이다. 앱에 고정 비밀번호를 넣거나 APK 링크를 숨기는 것만으로 제한하지 않는다.

- 기존 익명 로그인에서 받은 access token을 Supabase Auth `/user`로 검증하고 `sub`·`session_id`·익명 여부·만료·최대 세션 나이를 확인한다.
- 검증된 사용자 `sub`의 서버 가명값을 service-role 전용 허용 목록과 비교한다. 목록은 RLS와 권한 제한으로 클라이언트가 조회·수정할 수 없게 한다. 발급·조회·생성 및 모델 호출 전에 확인하고 허용되지 않으면 호출·예산 차감 없이 차단한다. 원문 토큰, OpenAI 키를 기록하지 않는다.
- 테스터 등록은 운영자가 본인임을 확인한 테스트 설치의 익명 사용자 ID를 안전한 관리 경로로 받아 서버에서 추가한다. ID는 인증 수단이 아니다. 앱에는 등록 상태/거절 안내와 ID 복사 경로를 제공하되 토큰을 표시하지 않는다. 재설치 등으로 익명 사용자가 바뀌면 다시 등록한다. 사용자 식별과 등록 방식은 구현 전에 운영자가 확정한다.
- 테스트 모드와 공개 모드를 명시적으로 구분한다. `RECIPE_PUBLIC_POLICY_APPROVED`를 테스트를 위해 허위로 `true`로 설정하지 않는다. 서버 기본값은 비활성/차단이며, 공개 정책 미승인 상태에서도 **허용 목록과 테스트 예산이 강제되는 경우에만** 테스트 모드를 허용하도록 별도 분기를 설계·검증한다. 기존 공개 모드의 정책 검사는 우회하지 않는다.
- 기존 IP 제한은 신뢰 경계가 검증된 헤더를 사용할 때만 운영한다. Supabase gateway가 외부 제공 값을 제거·덮어쓰는지와 우회 경로를 검증하기 전에는 임의 헤더를 신뢰하지 않는다. 검증이 불가능하면 안전한 프록시 또는 동등한 서버 측 보호를 구현하고 제한 테스트를 열지 않는다. 로그인 생성 남용은 Auth 자체의 제한으로 별도 보호한다.
- 운영자는 테스터 추가·제거, 전체 테스트 중지, 예산과 오류 확인을 할 수 있어야 한다. 중지 시 진행 중 호출의 취소·환불은 보장하지 않는다. 테스트 종료 후 추천을 다시 비활성화하는 절차를 준비한다.

## 5. 비용과 모델 호출

- 이미 허용된 실제 OpenAI 테스트 전체 한도는 **누적 $0.50**이다. 이전 PC 및 임시 함수 호출의 확인 가능한 사용량을 포함해 남은 한도를 계산하고, 불명확한 비용은 보수적으로 잡는다. 청구 대시보드 수치가 없으면 실제 청구액이 확정됐다고 표현하지 않는다.
- OpenAI의 현재 모델 접근성과 입력·출력 가격을 실행 직전 공식 가격 정보로 확인한다. 기존 테스트의 가격 가정은 현재 가격의 증거가 아니다. 가격 확인 전 예산 가드를 활성화하지 않는다.
- 입력 65,536바이트와 여유 1,000, 호출당 출력 최대 4,000토큰, 최초 1회 + 전체 결과 검증 실패 시 교정 최대 1회에 대한 기존 최대 예약 공식을 사용한다. 두 호출 모두 예산을 미리 예약하고 원자적으로 차감한다. 시간 초과 등 사용량 불명은 예약액 전액을 보수적으로 반영한다. 남은 한도보다 예약액이 크면 호출하지 않는다.
- 테스트 중 전체 동시 작업 1, 세션별 동시 1, 기존 한국 시간 하루 5회 이하를 적용한다. DB 일일·월간 예산은 누적 테스트 한도를 넘지 않게 별도로 설정하고, OpenAI 프로젝트 지출 한도도 확인한다. 외부 서비스 요금·세금과 대시보드 집계 지연은 별도임을 명시한다.
- 같은 세션·작업 ID·입력 재전송은 기존 상태/결과만 반환한다. 입력이 바뀌면 충돌, 만료된 ID는 재실행하지 않는다. 실패·타임아웃이 났다고 자동으로 새 작업을 만들지 않는다.

## 6. 데이터와 보관

- Flutter 앱에는 Supabase URL과 공개 publishable key만 포함한다. OpenAI 키·service-role 키·관리 토큰·테스터 관리 권한은 서버/관리 환경에만 둔다.
- 재료 원문·제외 원문·토큰·키는 일반 로그와 분석 이벤트에 남기지 않는다. 서버는 입력 해시 및 필요한 가명 메타데이터만 저장하며, 결과는 세션/요청에 결합해 암호화한다.
- 결과 조회는 같은 세션으로 제한하고 발급 후 24시간이 지나면 제공하지 않는다. 활성 유지보수 작업이 만료 ciphertext를 삭제하고 예약 복구·속도 제한 정리를 수행한다. 삭제 지연, 관리형 백업, 영구 가명 tombstone 및 삭제 요청 처리는 개인정보 안내에 명확히 기재하고 테스트와 공개 범위에 맞게 결정한다. `store: false`만으로 OpenAI의 모든 보관이 없어진다고 주장하지 않는다.

## 7. 구현과 검증 순서

1. Git 상태·현재 원격 설정·기존 마이그레이션을 읽고 기존 사용자 변경을 보존한다. 기존 키·암호화 키를 교체하지 않는다.
2. 허용 목록과 테스트 모드의 접근·차단, 사용자 ID 등록 방법, 예산 설정 및 신뢰 IP 경계를 확정해 기존 DB에 추가 마이그레이션을 작성한다. 테스트/공개 모드가 서로 섞이지 않도록 기본 차단과 롤백을 구현한다.
3. 실제 모델 호출 없이 단위·통합 테스트로 허용/거절·토큰 위조·재설치·동시 작업·예산 경쟁·중복 요청·불명 비용·만료/정리·민감정보 로그를 검증한다. 앱의 오류 표시·취소·입력 보존·즐겨찾기·재고 트랜잭션도 확인한다.
4. 승인된 새 프로젝트에서 테스터 한 명을 등록하고 위 예산 이내로 실제 앱→Auth→issue→reserve→OpenAI→검증→암호화 저장→앱 결과 표시를 최소 1회 성공시킨다. 앱 재시작 후 같은 세션 결과 조회, 잘못된 사용자 차단, 사용량과 예약/정산, 정상 `no_match` 또는 통제된 오류를 검증한다. 테스트 횟수·토큰·확인 가능한 비용과 남은 불확실성을 보고한다.
5. 실제 Android 기기에서 재고 입력부터 결과 표시, 즐겨찾기·장보기·조리 기록과 기존 설치의 업데이트/데이터 유지 여부를 확인한다. 에뮬레이터·서버 스크립트 검증만으로 실제 기기 성공이라고 주장하지 않는다.
6. 같은 앱 ID와 기존 인증서, 증가한 versionCode로 APK를 빌드하고 `apksigner`·`aapt`·SHA-256을 확인한다. 테스트와 리뷰가 통과하면 소스는 GitHub에 커밋하고 APK는 Git에 넣지 않은 채 테스트용 사전 릴리스에 첨부한다. 실제 추천이 실패하거나 접근 제한·비용 가드가 불완전하면 추천 가능 테스트 빌드라고 배포하지 않는다. 공개 서비스 승인은 이 테스트와 별개다.

## 8. 수용 기준

- [ ] 허용된 테스터가 앱에서 실제 AI 추천 1회 이상을 성공하고 결과/상세를 본다.
- [ ] 비허용·위조·만료 세션은 모델 호출 전에 차단된다. 앱 공유만으로 테스트 권한을 얻을 수 없다.
- [ ] 누적 테스트 예산 $0.50을 넘지 않도록 예약·정산하고, 한도 도달 시 추가 호출을 차단한다.
- [ ] 결과 검증·중복/재시도·재고 보호·오류 처리가 자동화 테스트와 실제 흐름에서 확인된다.
- [ ] 선택된 입력과 보관·안전 한계를 사용자에게 안내하고 비밀키가 앱·Git·일반 로그에 없다.
- [ ] 원본 서명/앱 ID/증가한 versionCode를 확인하며 기존 앱을 삭제하라고 안내하지 않는다.
- [ ] 테스트 접근, 개인정보 안내, IP 신뢰 경계 및 테스트 종료 후 차단을 운영자가 검토한다.

## 9. 운영자 결정이 필요한 사항

1. 제한 테스트에 참여할 사람/기기와 익명 사용자 ID 등록·회수 방법. 권장: 우선 소유자 1명, 필요 시 추가.
2. 테스트용 개인정보·OpenAI 전송 안내의 내용과 제공 위치. 기존 앱 내 최초 전송 안내를 기초로 검토한다.
3. Supabase의 신뢰 가능한 사용자 IP 경계 또는 대체 보호 방식. 검증되지 않으면 기존 기능을 억지로 활성화하지 않는다.
4. 실제 기기 테스트 가능 여부와 기존 앱 데이터 보존 확인 담당자.
5. 공개 서비스로 확대할 때의 별도 일일·월간 운영 예산, 남용 방지·정책 및 출시 판단. $0.50 테스트 허용은 공개 운영 예산 승인이 아니다.

구현 결정: 등록 코드는 서버가 Auth 검증 후 발급한 HMAC 가명값을 사용한다. 제한 테스트의 IP 보호 대안은 허용 목록과 검증 사용자별 속도 제한으로 구현했으며 공개 모드의 IP 신뢰 검사를 완화하지 않는다. 상세 운영/실측: [테스트 운영](../../AI_RECIPE_PILOT.md).
