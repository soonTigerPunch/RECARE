## 1 현재 개발 상태

RE:CARE는 식재료의 등록부터 소비·폐기와 주간 폐기금액 확인까지 연결한 오프라인 Flutter MVP다. 기존 Kotlin 앱의 핵심 기능과 저장 규칙을 Flutter로 이전했고, 홈·목록·설정 화면과 수량 선택 방식을 개선했다. 현재 개발 기준은 RECARE_flutter 프로젝트이며, 서버·로그인 없이 기기에 데이터를 저장한다.

공개 배포본은 2026년 10월 14일 게시한 v1.0.2-mvp다. 이후 적용한 안내 문구와 관련 화면 캡처 수정은 로컬 작업 상태이며, 공개 APK에는 아직 포함되지 않았다. 자동완성은 대표 상품과 이전 등록 이력을 사용하는 방향으로 합의했지만 구현하지 않았다.

### 대표 동작

우유 1L를 3,000원에 등록하고 250ml를 폐기하면 재고는 750ml, 해당 폐기금액은 750원이다. 구매금액을 입력하지 않았다면 0원으로 바꾸지 않고 ‘금액 미입력’으로 남긴다. 소비 기록은 재고를 줄이지만 주간 폐기금액에는 더하지 않는다.

## 2 개발 경과와 초기 환경 정리

### 범위 확정부터 Flutter 전환까지

2026년 10월 12일에는 기능을 넓히기보다 등록·목록·소비 및 폐기·주간 집계의 흐름을 먼저 연결하기로 했다. 첫 저장 방식은 기기 내 SQLite로 정했고, 테스트 가능한 Android APK를 우선 결과물로 삼았다. 이 기준으로 Kotlin MVP를 구현한 뒤 사용자의 요청에 따라 Flutter로 전환했다.

마이그레이션 준비 단계에서는 Flutter SDK, Dart, Android 도구와 라이선스를 확인하고 사용자 PATH에 Flutter 경로를 추가했다. 기존 소스·APK와 데이터베이스 스키마, Dart 계산 코드 및 확인용 자료를 보존했다. 사용자가 지정한 실제 이전 대상은 AndroidStudioProjects 아래 RECARE_flutter 폴더다.

## 4 핵심 기능과 계산 규칙

### 등록과 목록

이름, 양수 수량, 단위, 소비기한을 입력하며 전체 등록 수량의 구매금액은 선택 항목이다. ml·L·g·kg·개를 지원하고 일반 수량 입력은 소수점 셋째 자리까지 받는다. 목록은 소비기한이 빠른 순서로 정렬하고 같은 날짜에서는 이름을 비교한다. D-Day, D-N, N일 지남을 표시하며 재고가 없는 재료는 ‘모두 처리됨’으로 구분한다.

### 수정과 삭제

| 조건 | 수정 가능 범위 | 삭제 동작 |
| --- | --- | --- |
| 처리 기록 없음 | 이름·수량·단위·소비기한·구매금액 | 확인 후 삭제 가능 |
| 먹음 또는 폐기 기록 있음 | 이름·소비기한 | 삭제 차단, 기존 기록 보존 |
| 이미 삭제된 재료 | 해당 없음 | 반복 삭제가 다른 데이터에 영향을 주지 않음 |

기록이 생긴 뒤에는 과거 금액의 기준이 달라지지 않도록 수량·단위·구매금액을 잠근다. 추가 구매분은 새 식재료로 등록한다. 기록이 있는 재료의 남은 재고는 먹음·폐기로 처리하며, 기록 자체를 삭제하거나 무시해 집계가 바뀌는 방식은 채택하지 않았다.

### 소비와 폐기 처리

처리 수량만큼 재고를 줄이고 처리 당시의 이름·날짜·수량·단위·금액을 기록한다. L와 ml, kg과 g 사이 변환을 지원한다. 0 이하 수량, 재고를 넘는 수량, 다른 종류의 단위, 미래 처리 날짜는 저장을 거부한다.

수량은 0.001ml·g·개 단위의 정수로 저장한다. 금액은 BigInt 정수 연산을 이용한 누적 비례 반올림으로 배분한다. 예를 들어 3개 100원을 한 개씩 모두 처리하면 33원·34원·33원으로 총액 100원이 보존된다. 과거 기록은 처리 당시의 값을 저장하므로 이름을 수정해도 이전 기록의 이름·금액은 바뀌지 않는다.

재고 갱신과 기록 추가를 한 트랜잭션으로 묶었다. 저장 중 실패하면 두 작업을 함께 되돌리고, 같은 요청 ID를 재시도해도 재고를 다시 줄이지 않는다. 저장 중 버튼을 비활성화하고 완료 전 중복 조작을 막는다.

### 주간 폐기금액

기기 날짜 기준 월요일부터 오늘까지의 WASTE 기록만 더한다. 먹음 기록, 이전 주 기록, 미래 날짜 기록은 제외한다. 화면에 표시하는 주간 날짜 범위는 월요일부터 일요일까지지만, 실제 합계에는 오늘까지의 기록만 들어간다.

금액이 없는 기록은 별도 건수로 보여준다. 일부만 금액이 있으면 입력된 금액만 합산했다고 안내하고, 모든 폐기 기록이 금액 미입력이면 총액도 ‘금액 미입력’으로 표시한다. 기록이 없는 주의 0원은 실제 낭비가 없었다는 보장이 아닌 등록된 기록 기준의 결과다.

## 5 화면 구조와 조작 방식 개선

| 화면 | 주요 정보 | 이어지는 행동 |

홈의 우선 확인 대상은 소비기한이 지났거나 3일 이내인 재료다. 최대 4개를 보여주고 더 있는 경우 나머지 개수를 안내한다. 상세 화면에는 이름, 소비기한, 남은 재고, 먹음·폐기 버튼, 구매금액, 등록 정보와 처리 내역을 배치했다.

### 최소한의 디자인 규칙

팀의 선택을 반영해 슬레이트 블루 #526984를 주색, 세이지 그린 #526D58을 보조색으로 사용했다. 불필요하게 여러 카드로 나누지 않고 정돈된 행과 구분선·여백으로 식재료를 구분한다. 이름을 먼저 읽고 소비기한과 D-Day를 이어 확인하도록 배치했다.

색상, 글자 크기, 간격, 모서리 규칙을 lib/ui/design_system.dart에 모았다. 공통 간격은 4·8·12·16·24·32, 입력·버튼 모서리는 12, 대화상자는 16을 사용한다. 주요 정보에 따라 글자 크기와 굵기를 나누고 수량·금액은 오른쪽에 정렬했다. 장식용 그래프나 의미 없는 배지는 추가하지 않았다.

### 수량 선택 개선

직접 입력 중심의 처리 화면을 전부·절반·1/3·1/4 버튼과 별도의 직접 입력 버튼으로 바꿨다. 비율은 최초 등록량이 아니라 현재 남은 재고에 적용한다. 처음에는 비율을 자동 선택하지 않아 의도하지 않은 저장을 방지하고, 유효한 수량을 정한 뒤 저장할 수 있게 했다.

남은 우유가 750ml일 때 절반은 375ml다. 1L의 1/3은 내부 최소 단위에 맞춘 333.333ml가 되며, 직접 입력으로 바꿔도 같은 양을 유지하도록 ml·g 같은 기본 단위로 전환한다. 저장 전에 처리 수량·금액·처리 후 재고를 보여준다. 너무 작은 비율로 결과가 0이 되면 직접 입력을 안내한다.

### 설정과 화면 안정성

화면 모드와 처리 완료 표시를 별도 JSON 파일에 저장해 재실행 후 복원한다. 연속 변경은 순서대로 저장하고 임시 파일 작성 후 교체한다. 설정 불러오기 실패 시 조작을 제한하고 재시도를 제공하며, 실패가 식재료 DB를 초기화하지 않도록 했다.

화면 복귀와 날짜 변경을 반영해 소비기한 표시와 주간 기준을 갱신한다. 작은 화면과 큰 글자에서 핵심 동작에 접근할 수 있도록 스크롤·줄바꿈·가변 너비를 사용한다.

## 6 앱 내부 문구와 화면 자료

### PDF 초안의 적용 원칙

앱 내부 문구 초안을 읽고 등록·목록·홈·삭제 확인에 필요한 안내만 적용했다. ‘식품’은 ‘식재료’, ‘유통기한’은 ‘소비기한’으로 통일했다. 일반 안내와 기존 도움말은 한 화면 최대 3개로 제한했다. 입력 항목명, 실제 수량·금액, 버튼명, 필요한 입력 오류는 일반 안내 문구와 구분한다.

| 위치 | 반영한 문구와 동작 |
| --- | --- |
| 신규 등록 | ‘냉장고에 보관 중인 식재료를 등록해보세요.’ 기존 수량·금액 도움말과 함께 최대 3개 |
| 재료가 있는 목록 | ‘식재료를 선택하면 상세 정보를 확인할 수 있어요.’ |
| 처음 비어 있는 목록 | ‘아직 등록된 식재료가 없어요.’와 등록 안내 |
| 완료 재료만 남은 목록 | 보관 중인 재료가 없다고 알리고 설정의 처리 완료 표시 안내 |
| 홈 | 소비기한이 지났거나 3일 이내인 재료의 확인 안내, 재고 없음과 임박 재료 없음 구분 |
| 삭제 확인 | 식재료 이름 다음에 ‘냉장고 목록에서 삭제할까요?’ 표시 |

설정과 주간 폐기 화면은 기존 안내가 충분해 추가 문구를 넣지 않았다. 문서의 AI 사진 인식·알림·레시피·네트워크 안내는 구현되지 않은 기능을 약속하므로 적용하지 않았다. 날짜만으로 섭취 안전성을 단정하는 ‘여유롭게 먹을 수 있어요’ 같은 표현도 제외했다.

### 로컬 변경 범위

최신 문구 적용은 lib/main.dart와 docs/screenshots의 home.png, home-dark.png, fridge.png, registration.png에 반영되어 있다. 저장 스키마·금액 계산·삭제 보호 정책은 변경하지 않았고 라이브러리도 추가하지 않았다. 기준일 현재 이 5개 파일은 공개된 최초 커밋 이후 로컬 수정 상태다.

### 화면 자료 제작

현재 구현 화면을 테스트 데이터로 렌더링해 홈, 목록, 등록, 상세, 비율 처리, 직접 입력, 주간 폐기, 설정, 다크 설정, 다크 홈의 10개 PNG를 만들었다. 원본은 1080×2340이며 360×780 화면 크기에서 3배로 출력한 것이다. 실제 기기를 촬영한 이미지와 구분한다.

별도 공유용으로 홈·목록·등록·상세·수량 선택·주간 폐기의 핵심 6장과 모음 이미지를 ZIP으로 정리했다. 기존 핵심 6장 ZIP은 문구 수정 전 자료이며, 최신 안내 문구는 Flutter 프로젝트 docs/screenshots의 해당 이미지에서 확인한다. 이전 마이그레이션 문서의 ‘5화면’ 표기는 초기 확인 범위이고 현재 저장된 화면 자료는 10개다.

## 9 후속 기능 합의와 미구현 범위

### 자동완성의 첫 범위

사용자는 이름 일부를 입력하면 사진이 있는 상품 제안을 보여주고, 선택한 상품의 이름·용량 같은 기본 정보를 등록 화면에 채우는 기능을 제안했다. 논의한 선택지는 이전 등록 이력만 사용, 대표 상품과 이전 이력을 함께 사용, 다양한 시판 상품을 외부에서 검색하는 방식이었다.

최초 구현 방향은 두 번째인 ‘팀이 준비한 대표 상품 + 사용자의 이전 등록 이력’으로 합의했다. 예시는 ‘서울우…’ 입력 후 상품명·사진·용량이 있는 제안을 선택하는 흐름이다. 기준일 현재 상품 DB, 검색 UI, 이미지 연결, 캐시 또는 외부 검색 서버는 추가되지 않았다.

### 합의 후 설계에서 정할 사항

- 대표 상품의 초기 목록, 사진 확보 경로와 사용 가능 범위, 상품별 용량 구분
- 이름·브랜드·용량·이미지를 담는 상품 정보와 개별 재고 기록의 연결 방식
- 최근 사용·일치도 등 제안 순서, 검색 결과가 없을 때 직접 입력 흐름
- 이전 등록 이력을 어느 범위까지 재사용할지와 품목 중복 처리
- 상품 목록 갱신과 이미지 용량 관리, 실제 기기에서의 검색 성능 확인

소비기한과 구매금액은 같은 상품을 다시 사도 달라진다. 상품 선택으로 이름·용량을 채우더라도 이번에 산 제품의 소비기한과 실제 결제금액을 별도로 확인하는 방안을 제안했다. 참고 가격이 생겨도 실제 구매금액과 분리해 폐기금액 계산에 추정치가 섞이지 않도록 해야 한다. 이 내용은 상세 구현 설계에서 확정할 사항이다.

### AI 모델에 대한 논의

소비기한·가격 예측 모델의 가능성을 논의했지만 모델 개발이나 학습은 시작하지 않았다. 상품명만으로 개별 제품의 소비기한을 정하지 않고, 가격도 실제 구매금액을 대체하지 않는 방향을 권고했다. 향후 포장의 날짜를 읽고 사용자가 확인하는 방식이나 소비 이력을 이용한 구매량 추천은 검토 아이디어로 남아 있다.

### 기존 후속 범위

사진 첨부, 하루 한 번 임박 재료 요약 알림과 기준·켜기 설정, 보유·임박 재료 기반 AI 레시피 및 실패 시 재시도 안내는 미구현이다. 사진 자동 인식·바코드·공개 가격 데이터·로그인·동기화도 현재 MVP에 포함되지 않는다. 기기 내 수기 입력을 기반으로 하고, 다음 기능은 자동완성 범위를 구체화한 뒤 연결한다.

### 다음 확인 순서

1. 대표 상품과 이미지의 준비 범위를 정하고 자동완성 데이터 구조·화면 흐름을 확정한다.
2. 기존 재고·처리 기록·금액 계산을 보존하면서 검색과 선택 동작을 연결한다.
3. 최신 문구와 후속 변경을 포함한 새 APK를 만들고 실기기 전체 흐름을 확인한다.
4. 공개 소스와 Release의 버전·변경 설명을 함께 갱신한다.

## 11 자동완성 구현 추가 업데이트

2026-10-17 · 로컬 앱 버전 **1.0.3+4**. 이 절은 앞선 자동완성 미구현 상태 이후의 변경이다.

### 구현한 흐름

신규 식재료 등록에서 이름을 입력하면 대표 이미지, 이름, 수량·단위와 출처를 함께 제안한다. 선택하면 이름과 수량·단위를 채운다. 대표 상품 3개 용량과 일반 식재료 19개를 앱에 포함하고, 최근 등록 이력 최대 200개를 함께 검색한다. 검색 결과는 최대 5개이며, 글자를 입력할 때마다 DB를 조회하지 않고 등록 화면을 열 때 한 번 불러온 메모리 목록을 검색한다.

이전 등록 이력은 남은 재고가 아닌 최초 등록량을 사용한다. 동일 이름·단위 종류·수량은 최근 이력을 우선하며 계란/달걀 같은 별칭도 유지한다. 다 먹거나 폐기한 재료도 재등록할 수 있다. 결과가 없어도 직접 입력할 수 있으며 이력 조회 실패 시 기본 목록을 유지하고 재시도를 제공한다.

### 구매 정보와 기존 기록 보존

제안에는 과거 소비기한과 구매금액을 넣지 않는다. 제안을 선택하면 이미 입력한 소비기한·구매금액도 비워 새 구매 기준으로 확인하도록 한다. 가격을 비워두면 기존처럼 NULL과 ‘금액 미입력’으로 처리한다. 시장가와 AI 예측값은 계산에 넣지 않는다.

자동완성은 신규 등록에서만 제공한다. 기존 재료의 수정 제한, 기록 없는 재료만 삭제하는 정책, 먹음·폐기 처리와 주간 금액 계산은 유지한다. Food 모델, SQLite 버전·테이블 및 기존 기록의 데이터 마이그레이션은 변경하지 않았다.

### 이미지와 제품 범위

이미지는 직접 그린 가벼운 대표 벡터 일러스트이며 실제 상품 사진이 아니다. 제안과 선택 안내에 ‘대표 이미지’를 표시하고 상세 화면도 저장된 이름에 맞춰 그림을 표시한다. 이름을 바꾸면 해당 이름 기준으로 그림이 바뀐다. 별도 사진 첨부나 이미지 DB 컬럼은 추가하지 않았다. 일반 식재료의 양은 수정 가능한 ‘기본 입력량’이다. 서울우유 저지방 3개 용량의 근거와 상세 설계는 [AUTOCOMPLETE.md](AUTOCOMPLETE.md)에 기록했다.
