# RE:CARE Flutter 마이그레이션

대상: `RECARE Flutter 프로젝트 폴더`

## 구현 범위

서버 없이 기존 Kotlin MVP 기능 1~4를 이전했다.

- 이름·수량·단위·소비기한·선택 구매금액 입력 및 SQLite 로컬 저장.
- 소비기한순 행 목록, D-Day, 상세·수정·삭제, 재고 0인 재료 확인.
- 먹음·폐기 수량·날짜·금액 기록과 재고 감소.
- 월요일부터 오늘까지 실제 폐기 기록의 내역·금액 합계.
- 금액 미입력과 0원 구분, 단위 변환, 재고 초과·미래 처리 날짜 차단.
- 처리 기록이 생긴 재료는 이름·소비기한만 수정. 추가 구매분은 새 재료로 등록.
- 삭제는 처리 기록이 없는 재료에만 적용한다. 기록이 있으면 삭제를 막아 주간 집계와 처리 내역을 보존한다.
- 슬레이트 블루와 세이지 그린을 사용하며 글자·색상·간격·모서리를 공통 테마로 관리한다.

아래 내용은 기존 Flutter 이전 시점의 기록이다. 이후 로컬 알림·소비기한 확인·AI 레시피를 추가한 변경은 문서 하단에 기록한다.

## 기존 데이터 호환

앱 ID `com.detabev.recare`, 데이터베이스 `recare.db`, 버전 1, 테이블·컬럼·단위/처리 코드를 그대로 유지했다. `onCreate`만 새 DB를 생성하며 기존 DB는 초기화하지 않는다. 현재 앱 버전은 `1.0.2+3`다.

부분 처리 금액은 BigInt 정수 연산으로 누적 비례 반올림한다. 우유 1L·3,000원 중 250ml 폐기 시 남은 재고 0.75L(750ml), 폐기 금액 750원이다. 먹음 금액은 주간 폐기 합계에서 제외한다. 금액 미입력은 SQL NULL로 보존한다.

기존 앱을 업데이트할 때는 같은 서명으로 설치해야 한다. 기존 앱을 삭제하면 DB도 삭제되므로 삭제 후 재설치하지 않는다. 실제 Android 앱 업데이트 시 데이터 유지 검증은 기기 연결 후 수행한다.

## 2026-10-14 화면 개선

홈·목록·설정 3개 탭으로 구성한다. 홈은 실제 기록에서 이번 주 폐기금액을 계산하고 소비기한 3일 이내·지난 재료를 보여준다. 목록의 식재료를 누르면 상세·수정·삭제와 먹음·폐기로 이동한다.

처리 수량은 전부·절반·1/3·1/4 또는 직접 입력으로 지정한다. 비율은 현재 남은 재고 기준이며 최소 내부 단위로 반올림한다. L·kg의 작은 비율은 ml·g로 표시해 직접 입력으로 전환해도 정확한 수량이 유지된다. 처리 수량·금액·처리 후 재고를 저장 전에 보여준다.

화면 모드와 처리 완료 표시 설정은 별도 recare_preferences.json 파일에 저장한다. 식재료 DB 버전·모델·금액 계산은 그대로 유지했다. 설정 저장 오류는 안내와 재시도로 처리한다.

## 2026-10-21 일상 사용성 저장 확장

스키마 버전 2를 추가했다. 버전 1의 기존 foods·records와 금액 NULL을 유지하며 records에 waste_reason(선택 사유)과 voided(실행 취소 표시)를 추가하고 shopping 테이블을 생성한다. 되돌린 요청 ID도 남겨 재시도에 의한 중복 처리를 막는다. 집계는 유효 기록만 사용한다. 상세한 동작은 [일상 사용성 기능](EVERYDAY_USABILITY.md)을 참고한다.

클라우드 debug APK의 서명은 기존 PC의 debug 서명과 다를 수 있다. 기존 설치를 유지한 업데이트에는 같은 서명 키가 필요하며, 이 작업에서 기존 기기의 앱을 삭제하거나 데이터를 초기화하지 않았다.


## 2026-10-22 소비기한 확인 이력

앱 버전 1.1.0+5, SQLite 버전 3. `expiry_check_ins`에 재료·소비기한·확인일·답변·요청 ID·선택적 먹음 기록 ID를 저장한다. v1에서 v3으로 직접 이전하거나 v2에서 이전할 수 있다. 소비량 답변은 기록·재고·확인 표시를 원자적으로 저장한다. 처리 이력 없는 재료 삭제 시 해당 확인 이력은 함께 정리한다. 이미 답한 재료는 같은 날 다시 묻지 않으며 소비기한이 변경되면 새 날짜 기준으로 확인한다.

## 2026-11-05 AI 레시피 저장 확장

SQLite 버전 4는 기존 `foods`, `records`, `shopping_items`, `expiry_check_ins`를 유지한다. v1·v2·v3에서 순서대로 필요한 확장만 적용하며 기존 테이블을 초기화하지 않는다. 이전 버전 앱으로 낮춰 열면 데이터 손실을 방지하기 위해 실패한다.

추가 테이블은 `recipe_values`(전송 안내 버전·명시 보유 양념·인분·시간·익명 세션), `recipe_recent`(최근 요청 결과 5회), `recipe_favorites`(독립 레시피 본문 최대 100개와 저장 시각), `recipe_cooking`(영속 조리 작업 ID·날짜·재고 스냅샷·상태), `recipe_cooking_records`(해당 먹음 기록 연결), `recipe_shopping_batches`(장보기 일괄 요청과 처리 결과)다. 원문 알레르기·제외 입력은 요청 메모리에만 유지하고 이 저장 구조에 복사하지 않는다. 생성 본문에 조건이 간접 반영될 수는 있다.

레시피 저장소는 기존 재고 저장소와 같은 SQLite 연결을 사용한다. 조리 작업과 사용량 초안을 먼저 저장하고, 완료 시 날짜·이름·단위·소비기한·남은 재고를 포함한 전체 스냅샷을 재검증한다. 먹음 기록·기존 정수 금액 배분·재고 차감·작업 완료를 한 트랜잭션으로 처리한다. 재시작 후 같은 완료 요청은 기존 건수를 반환하며 재차 차감하지 않는다. 새 조리 회차만 명시적으로 새 작업 ID를 만든다. 원래 연결한 보관분이 사라지면 이름이 같은 다른 보관분으로 자동 대체하지 않는다.

일괄 실행 취소는 연결된 모든 기록이 재료별 최신 유효 기록이고 복원 가능할 때만 전체 적용한다. `voided=1` 기록과 작업 상태를 보존하여 재시도가 차감이나 복원을 반복하지 않는다. 장보기 일괄 추가도 같은 연결에서 요청 ID와 항목 내용을 확인하고 전체 성공 또는 전체 롤백한다. 기존 이름·단위 계열·정수 수량 중복 규칙을 유지한다.

합성 DB 기반 테스트에서 v1/v2/v3 데이터 유지, 즐겨찾기 독립 저장과 재시작, 저장 한도, 조리 재시도, 스냅샷 변경 거부, 중간 차감·실행 취소·장보기 저장 실패의 전체 롤백을 검증한다. 실기기 업데이트 설치나 실제 모델 호출을 검증한 결과는 아니다.

숫자 수량과 단위가 있는 재료는 검증한 정수값에서 표시 수량을 다시 계산한다. 저장된 과거 본문을 열어도 같은 규칙을 적용해 모델의 표시 문구와 실제 조리 차감량이 달라지지 않게 한다. 숫자 수량·단위가 모두 없는 경우에만 '약간' 같은 원래 문구를 유지한다.
